# 블로킹 쿼리 관계 조회

## 1. 핵심 요약
- `pg_blocking_pids()`와 `pg_stat_activity`를 조인하여, 현재 어떤 쿼리가 어떤 쿼리를 블로킹하고 있는지 한눈에 확인하는 PostgreSQL 잠금 진단 쿼리.

## 2. 상세 설명

### 배경

PostgreSQL에서 여러 트랜잭션이 동시에 같은 로우(또는 테이블)에 접근할 때 잠금 충돌이 발생할 수 있다. 잠금이 걸린 쿼리는 선행 트랜잭션이 끝날 때까지 대기 상태로 멈춘다. 이 상태를 빠르게 파악하려면 아래 쿼리를 사용한다.

### 조회 쿼리

```sql
SELECT
    blocked.pid,
    blocked.usename,
    blocked.query AS blocked_query,
    blocking.pid AS blocking_pid,
    blocking.query AS blocking_query
FROM
    pg_stat_activity AS blocked
JOIN
    pg_stat_activity AS blocking ON blocking.pid = ANY(pg_blocking_pids(blocked.pid))
WHERE
    CARDINALITY(pg_blocking_pids(blocked.pid)) > 0;
```

### 핵심 함수·뷰

| 요소 | 설명 |
|------|------|
| `pg_stat_activity` | 현재 서버에서 실행 중인 모든 프로세스(세션)의 상태를 보여주는 시스템 뷰 |
| `pg_blocking_pids(pid)` | 특정 PID를 블로킹하고 있는 PID 배열을 반환하는 함수 (PostgreSQL 9.6+) |
| `CARDINALITY(array)` | 배열의 원소 수를 반환. `> 0`이면 실제로 블로킹 중임을 의미 |

### 결과 해석 예시

```
 pid   | usename  | blocked_query         | blocking_pid | blocking_query
-------+----------+-----------------------+--------------+-------------------------------------------------------
 31328 | postgres | drop table lock_test; | 31892        | update lock_test set lock_name = 'D' where lock_id=1;
```

- PID 31328이 `DROP TABLE`을 시도했지만, PID 31892의 `UPDATE` 트랜잭션이 먼저 잠금을 점유하여 대기 중이다.
- 해소 방법: 블로킹 쿼리(31892)의 트랜잭션을 커밋/롤백하거나, `pg_terminate_backend(31892)`로 강제 종료한다.

### 활용 시점

- 장시간 응답 없는 쿼리가 발생했을 때 잠금 원인 파악
- DBA 모니터링 스크립트에 주기적으로 포함하여 잠금 이력 추적
